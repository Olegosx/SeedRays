# Наблюдение

Наблюдение за работающим шлюзом: на что смотреть, где журналы, как выглядят типовые
проблемы. Шлюз — один процесс, поэтому основной поток — его служебный лог плюс два
структурированных источника: журнал безопасности и блок состояния watcher в панели
оператора.

## Служебный лог

Под systemd лог процесса уходит в системный журнал:

```bash
journalctl -u seedrays -f
```

Формат: `время УРОВЕНЬ логгер: сообщение`. Что важно:

- `gateway starting: api on …` / `trusted reverse proxies: …` — строки старта с
  действующей привязкой и доверием прокси.
- `WARNING … exited unexpectedly, restarting` / `ERROR … crashed, restarting` —
  компонент (API-сервер или watcher) упал и перезапущен надсмотрщиком; редкие
  сетевые перезапуски watcher нормальны, цикл перезапусков — нет.
- Строки `ERROR` от отправки почты или провайдера цепочки — сбойная операция явно
  отвечена пользователю; лог несёт контекст для диагностики.

## Журнал безопасности

`logs/security.log` в каталоге данных
([ADR-0023](../20-architecture/decisions/0023-security-journal.md)): одна JSON-строка
на событие — события аутентификации с точными причинами, которые API сознательно не
раскрывает. Ротация по размеру, архивы сжаты gzip. Чтение:

```bash
tail -f /var/lib/seedrays/logs/security.log
```

```bash
jq -r 'select(.outcome != "success") | [.time, .actor, .event, .outcome, .identifier // "-", .client] | @tsv' \
    /var/lib/seedrays/logs/security.log
```

На что смотреть: серии `wrong_password` по одному идентификатору (прицельный
подбор), потоки `rate_limited` / `captcha_failed` (лобовой перебор — защита
работает), попытки `user_blocked` (заблокированный всё ещё стучится), операторские
события с неожиданных адресов.

## Watcher

Страница настроек панели показывает состояние watcher по сетям: последний
обработанный финализированный блок и время последнего прохода. У здорового шлюза
курсор блока движется, а время прохода обновляется каждый интервал
([ADR-0021](../20-architecture/decisions/0021-two-phase-scanning.md)). Замерший
курсор при свежем времени прохода означает, что провайдер не отдаёт новых
финализированных блоков — или ограничивает шлюз по частоте (см. служебный лог;
темп запросов — настройка панели).

## Разбор одного платежа

Пользователь говорит, что его платёж не дошёл. Ответить можно по служебному логу — не
заходя в консоль сервера и не открывая ни одной базы, потому что каждый проход пишет то,
что фактически сделал:

- строка на каждое **новое записанное** поступление — сеть, предварительное оно или
  финализированное, направление, сумма, актив, логин владельца, идентификатор транзакции,
  блок и адрес;
- строка на каждое поступление, **учтённое в балансе**, с теми же признаками;
- сводка прохода с **фактически просмотренными границами**: диапазон блоков (`blocks=`) и
  временное окно токенов (`tokens=`).

Найдите в логе идентификатор транзакции. Дальше три случая, и лечатся они по-разному:

1. **Есть строка о записи и строка об учёте в балансе.** Платёж у шлюза есть; смотрите
   фильтры кабинета и сам актив — токен вне списка `watcher.contracts.<сеть>` кабинет
   покажет, а в оборот для вознаграждения он не войдёт.
2. **Есть строка о записи, но нет об учёте.** Строка предварительная: финализированная
   зона до её блока ещё не дошла. Сравните блок с `blocks=` последующих проходов.
3. **Строки нет вовсе.** Проверьте, попадает ли блок в просмотренный диапазон. Ниже
   границы — провайдер перевод не отдал, нужна точечная сверка; выше — скан до него ещё
   не дошёл, и границы курсора показывают, насколько он отстаёт. Ровно для этого различия
   границы и пишутся.

## Типовые проблемы

| Симптом | Куда смотреть | Обычная причина |
|---------|---------------|-----------------|
| Регистрация отвечает `mail_not_configured` | настройки панели | Нет реквизитов почты или пуст `gateway.base_url` — отправитель без базового адреса не используется. |
| Письма не доходят, в ответах `mail_failed` | служебный лог | Почтовый сервис отказал: неверный ключ или домен в Resend не подтверждён (тогда доставка только владельцу учётной записи). |
| Все посетители упираются в лимит разом | `security.log`: у всех один `client` | Шлюз за прокси, не внесённым в `gateway.trusted_proxies`. |
| Поступления не появляются | состояние watcher, служебный лог | Замерший курсор (провайдер), нет списка `watcher.contracts.<сеть>` для токенов, либо приложению не настроено соответствие «сеть → кошелёк». По конкретному платежу — см. [Разбор одного платежа](#разбор-одного-платежа). |
| Курсор не двигается, хотя проходы идут | служебный лог | Проход не смог записать строки какого-то владельца и намеренно оставил курсор на месте, чтобы диапазон был просмотрен заново — лог называет владельца. Починить его базу, и курсор пойдёт дальше. |
| Строки нет в истории, а суммы занижены | служебный лог: `absent from the registry catalog` | Каталог реестра и база пользователя восстановлены из копий, снятых в разное время. Сами строки целы, не хватает описания актива. |
| После восстановления из бэкапа не войти в кабинет/панель | — | Сессии хранятся на сервере; база из бэкапа не знает выданных позже сессий. Войти заново. |
