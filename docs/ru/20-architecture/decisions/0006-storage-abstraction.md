# ADR-0006: Абстракция хранения на уровне операций предметной области

**Статус:** принято

## Контекст

Шлюз стартует на SQLite, далее должен поддержать PostgreSQL и MySQL. Бизнес-логика не должна
зависеть от выбранной базы.

## Решение

Доступ к данным идёт через интерфейс хранилища, определённый на уровне операций предметной
области («сохрани поступление», «дай адреса кошелька», «отметь адрес занятым»). Компоненты
выше интерфейса — оркестратор, watcher — SQL не видят вообще. Каждая реализация выполняет
операции своим диалектом. Первая реализация: SQLite (файл базы на пользователя, режим
журнала WAL); далее PostgreSQL и MySQL.

## Рассмотренные альтернативы

- **«Универсальный SQL» как абстракция:** отклонено — база протекает в бизнес-логику, а
  замена реализации усложняется; тот же принцип уже принят для абстракции блокчейна.
- **Прямые обращения компонентов к базе:** отклонено — привязывает логику к одной базе и
  превращает запланированную поддержку PostgreSQL/MySQL в переписывание.

## Открытые вопросы

- Библиотека реализации: SQLAlchemy Core + Alembic (один код на все три базы, инструмент
  миграций в комплекте; новая зависимость — по согласованию) или свой тонкий слой над
  стандартными драйверами (без зависимостей; три диалекта и миграции — на нас). Решается
  отдельным ADR на этапе реализации.
- Отображение изоляции «по пользователю» на PostgreSQL/MySQL — см.
  [ADR-0005](0005-multi-user-model.md).

## Последствия

- Базу можно сменить, не трогая бизнес-логику.
- Операции хранилища тестируются на временной SQLite-базе или базе в памяти.
- Интерфейс хранилища — единственное место, знающее схему данных.
