# ADR-0015: Провайдер данных TRON — TronGrid; интерфейс источника цепочки

**Статус:** принято; дополнено [ADR-0018](0018-range-scanning.md) — основным съёмом
становится диапазонное сканирование через точки событий контрактов и диапазонов блоков

## Контекст

По каждой сети watcher-у нужны текущая высота и переводы, наблюдаемые по адресу
([ADR-0007](0007-address-centric-watcher.md),
[ADR-0010](0010-networks-assets-financial-data.md)). Факты сверены с официальной
документацией (developers.tron.network, август 2026):

- **TronGrid** — официальный хостинг-сервис нод экосистемы TRON: и стандартные нодные
  вызовы, и заранее проиндексированные запросы «переводы по адресу» (у сырой ноды таких
  нет — иначе пришлось бы самим сканировать каждый блок).
- Базовые адреса: боевая сеть `api.trongrid.io`; тестовые — Shasta
  `api.shasta.trongrid.io` и Nile `nile.trongrid.io`.
- Бесплатный **API-ключ** создаётся в консоли TronGrid и передаётся заголовком
  `TRON-PRO-API-KEY`; у ключа собственные настройки безопасности (частота на ключ, списки
  разрешённых доменов/User-Agent/методов API). Без ключа доступ жёстко ограничивается
  (блокировки на 30 секунд, HTTP 403).
- **Точные квоты намеренно не публикуются**: «источник истины — консоль; не зашивайте
  лимиты в код» (исторически бесплатный план объявлял 15 запросов/сек и суточную квоту).
  Всплеск сверх частоты — HTTP 429. **Программного API для чтения своих квот нет.**
- Финальность: блок **солидифицирован**, когда на нём построили блоки 19 из 27
  супер-представителей — примерно минута позади головы цепочки.

## Решение

- **Провайдер — TronGrid.** Реализация вызывает документированные точки v1 — переводы
  TRC-20 по адресу, транзакции по адресу, `getnowblock` — через httpx.
- **Интерфейс источника цепочки** — две операции: `latest_block()` и
  `transfers(адрес, с_момента, только_подтверждённые)`, возвращающая нормализованные
  события перевода: ид транзакции, направление, сетеспецифичный актив с символом и
  десятичностью (корм автосправочника активов), сумма в минимальных единицах, номер блока,
  когда провайдер его сообщает, время и успех/провал.
- **Сети в коде: `tron` и `tron-nile`** — один путь кода, различие только в базовом URL.
  Какие сети активны — решение оператора конфигурацией; боевой экземпляр тестовую сеть не
  включает.
- **Темп запросов — настройка, а не константа в коде** (по прямой рекомендации
  провайдера): частота и суточный бюджет по провайдеру живут в настройках реестра,
  фактические числа оператор переносит из своей консоли TronGrid; значения по умолчанию —
  консервативные.
- **HTTP 429/403 классифицируются отдельной ошибкой «сбавь темп»**, отличимой от ошибок
  данных; политика выжидания и повторов — забота watcher.
- **Порог подтверждений — настройка на сеть; для TRON по умолчанию — 19** (в согласии с
  солидификацией).

## Рассмотренные альтернативы

- **TronScan API** (API обозревателя блоков): нестабильный недокументированный контракт —
  не для продакшена; отклонено.
- **Коммерческие нодные провайдеры** (QuickNode, GetBlock, …): платно, сырой доступ без
  индексации переводов — больше кода у нас за деньги; для старта отклонено.
- **Своя нода**: уже запланированный путь эволюции за той же абстракцией; отдельный ADR,
  когда придёт время.

## Последствия

- Проиндексированная точка TRC-20 не сообщает номер блока — событие несёт его как
  неизвестный; подтверждённость переводов TRC-20 опирается на солидифицированную выборку
  провайдера (`only_confirmed`).
- API-ключ — настройка шлюза в реестре ([ADR-0008](0008-shared-registry-db.md)); в коде,
  журналах и репозитории он не появляется никогда.
- Тесты работают на консервированных формах ответов из документации; живая проверка
  против Nile существует как тест с ручным включением.
