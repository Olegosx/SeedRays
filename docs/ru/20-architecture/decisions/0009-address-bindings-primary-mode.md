# ADR-0009: Постоянные привязки адресов как основной режим

**Статус:** принято; уточнено [ADR-0010](0010-networks-assets-financial-data.md) — привязка
получает колонку сети, уникальность включает сеть

## Контекст

Основное направление работы шлюза — не выставление единичных инвойсов, а постоянная привязка
платёжных адресов к аккаунтам подключённых приложений. У подключённого приложения есть свои
пользователи; его пользователь получает постоянную привязку к платёжному адресу, а владелец
приложения получает состояние внутреннего баланса этого пользователя через операции,
наблюдаемые по адресу. Единичные инвойсы будут реализованы позже.

## Решение

- **Приложение** — единица подключения к шлюзу: принадлежит пользователю шлюза и
  идентифицируется своим API-ключом.
- Основная сущность — **привязка**: кошелёк (тот, из чьего xpub выводится адрес), адрес,
  мемо (запасное поле для сетей, использующих мемо), приложение, пользователь приложения.
- **Пользователи приложения — отдельная таблица.** Идентификатор пользователя приложения —
  произвольная строка, которую присылает приложение; шлюз её не интерпретирует и
  обеспечивает уникальность в рамках приложения («юзер1» в приложении А и «юзер1» в
  приложении Б никак не связаны). Привязки ссылаются на внутренний id записи пользователя
  приложения.
- **Привязка хранит и прямую ссылку на приложение** — осознанная денормализация: фильтрация
  привязок по приложению — элементарная операция и не должна требовать прохода через таблицу
  пользователей приложения. Согласованность двух ссылок обеспечивается на уровне схемы.
- **Уникальность привязки:** кошелёк + приложение + пользователь приложения → одна привязка.
  В сетях с мемо много привязок могут разделять один адрес, различаясь мемо, поэтому
  привязку идентифицирует пара «адрес + мемо», а не адрес сам по себе.
- Таблица привязок — **таблица соответствия, финансовых данных не содержит** — колонки
  баланса в ней нет. Первоисточник сведений о средствах — журнал операций, наблюдаемых по
  адресам; балансы выводятся из него (структуры — на шаге проработки данных).

## Рассмотренные альтернативы

- **Инвойсная модель как основной режим:** отложено, не отклонено — единичные инвойсы будут
  добавлены позже поверх тех же структур.
- **Колонка баланса в привязке:** отклонено — финансовым данным не место в таблице
  соответствия.
- **Повторение строки пользователя приложения в каждой привязке вместо отдельной таблицы:**
  отклонено — уникальность пришлось бы обеспечивать во многих местах, строка дублировалась
  бы в каждой привязке, а будущим атрибутам пользователя приложения негде было бы жить.

## Последствия

- Рабочий список watcher — это список привязок, что согласуется с
  [ADR-0007](0007-address-centric-watcher.md).
- Запрос привязки для пользователя приложения — операция API приложений
  (см. [HTTP API](../components/http-api.md)).
- Детальная структура финансовых данных (балансы, транзакции) — следующий шаг
  проектирования.
