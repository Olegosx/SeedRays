# ADR-0024: Удаление пользователя — двухшаговое, через серверный архив

**Статус:** принято

## Контекст

Оператору нужен способ убрать пользователя из шлюза целиком — например, при
использовании шлюза для нелегальной деятельности. Простое стирание данных опасно:
ошибочное удаление уничтожило бы финансовую историю безвозвратно. При этом
архитектура делает перенос дешёвым: все данные пользователя живут в одном каталоге
([ADR-0005](0005-multi-user-model.md)), а в общем реестре
([ADR-0008](0008-shared-registry-db.md)) остаётся лишь несколько строк
(учётная запись, почты, индексы xpub и ключей API, сессии).

## Решение

- **Удаление двухшаговое: сначала блокировка, затем удаление.** Удалить можно только
  заблокированного пользователя — блокировка мгновенно отрезает доступ и гасит сессии,
  а удаление становится вторым, спокойным шагом; промах по строке списка не
  уничтожает живого пользователя.
- **Данные не стираются, а переезжают в архив** — каталог `archive/` внутри каталога
  данных шлюза, по подкаталогу на удаление (`<каталог>-<дата-время>`): снимок строк
  реестра (`registry.json` — учётная запись, почты, индексы xpub и ключей API) и
  каталог пользователя с его базой. Сессии и токены сброса пароля в архив не входят —
  восстановленный пользователь просто входит заново.
- Архив лежит **вне** `users/` сознательно: базы в `users/` миграции и watcher
  считают живыми, архивные базы трогать нельзя.
- **После удаления имя, почты, xpub и ключи API освобождаются** — их можно занять
  заново.
- **Подтверждение двойное**: в панели оператор набирает логин удаляемого руками, и
  сервер сверяет его ещё раз (`username_mismatch` при расхождении) — защита от
  ошибки на уровне и формы, и API.
- **Восстановление — только консольной командой** `seedrays user-restore --archive …`
  на сервере, не кнопкой панели: операция редкая и ручная. Строки реестра и каталог
  возвращаются на место; статус восстанавливается как был («заблокирован») —
  разблокировка остаётся отдельным действием оператора. Если что-то из
  освободившегося успели занять (логин, почта, xpub, ключ, id), команда честно
  называет конфликт и не делает ничего.
- Удаление пишется в журнал безопасности ([ADR-0023](0023-security-journal.md)):
  кто удалил, кого, в какой архив.

## Рассмотренные альтернативы

- **Безвозвратное стирание:** отклонено — ошибка оператора уничтожала бы финансовую
  историю; для платёжной системы неприемлемо.
- **«Мягкое» удаление флагом в базе:** отклонено — данные остаются в рабочем
  контуре (списки, обходы, бэкапы «живого»), а требование «выпилить из шлюза» не
  выполняется; блокировка как отдельный статус уже есть.
- **Удаление активного пользователя одним шагом с подтверждением:** отклонено —
  одно подтверждение хуже двух разнесённых во времени действий; блокировка ничего
  не разрушает и обратима мгновенно.
- **Восстановление кнопкой в панели:** отклонено — операция редкая, требует доступа
  к серверу по смыслу (архив лежит на диске) и не должна быть доступна из веба.

## Последствия

- В каталоге данных появляется `archive/`; он входит в резервную копию вместе со
  всем каталогом данных.
- Архив хранится бессрочно; чистка старых архивов — ручное решение владельца
  (автоматики сознательно нет).
- SQLite переиспользует освободившиеся id (таблица без AUTOINCREMENT), поэтому имя
  архивного подкаталога получает числовой суффикс при совпадении, а восстановление
  проверяет и занятость id.
- Журнал безопасности хранит имя удалённого пользователя и имя архива — след
  административного действия переживает саму учётную запись.
