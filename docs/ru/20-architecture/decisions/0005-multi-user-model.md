# ADR-0005: Многопользовательская модель — база и каталог на пользователя, три роли

**Статус:** принято; дополнено [ADR-0008](0008-shared-registry-db.md) — небольшая общая
реестровая база для нефинансовых общешлюзовых данных

## Контекст

Шлюз обслуживает нескольких пользователей. Многопользовательность влияет на базовую
архитектуру (устройство хранения, планирование watcher, модель доступа API), поэтому
откладывать её «на после MVP» означало бы протаскивать контекст пользователя через готовый
однопользовательский код — дорого и чревато ошибками (пропущенная проверка раскрывает чужие
данные).

## Решение

- Шлюз многопользовательский с самого начала, в полной реализации (включая интерфейсы), а не
  как доработка после MVP. Каждая операция оркестратора и каждый вызов хранилища несут
  контекст пользователя.
- У каждого пользователя — своя база данных (свой набор таблиц) и своя рабочая директория.
- Пользователь владеет одним или несколькими кошельками. Кошелёк — сущность со своим xpub;
  адреса, деривация и наблюдение привязаны к кошельку, а не к пользователю напрямую.
- Доступ разделён на три роли:
  1. **Оператор шлюза (суперадмин)** — управляет пользователями и общими настройками шлюза.
  2. **Пользователь (владелец кошельков)** — имеет личный кабинет; управляет своими
     кошельками и своими ключами приложений.
  3. **Приложения пользователя** — по API-ключу читают данные и запрашивают платёжные
     адреса в рамках кошельков владельца ключа.

## Рассмотренные альтернативы

- **Общая база с колонкой пользователя:** отклонено — изоляция держалась бы на дисциплине
  (каждый запрос обязан фильтровать по пользователю); базы на пользователя делают изоляцию
  структурной.
- **Однопользовательский MVP, многопользовательность потом:** отклонено — дорастить контекст
  пользователя задним числом дороже, чем строить с ним сразу.

## Последствия

- Структурная изоляция данных; резервная копия, перенос и удаление пользователя — операция
  над одним каталогом.
- Миграции схемы прогоняются циклом по всем пользовательским базам; инструментарий должен
  уметь это с самого начала.
- Сводные картины по всему шлюзу (статистика оператора) — обход N баз.
- Как изоляция «по пользователю» ляжет на PostgreSQL/MySQL (база или схема на пользователя) —
  открытый вопрос будущего ADR.
- HTTP API получает три группы маршрутов — по одной на роль; это расширяет
  [ADR-0004](0004-two-api-groups.md).
- Конкуренция записи в SQLite размазывается по файлам пользователей (см.
  [слой хранения](../components/storage.md)).
