# ADR-0004: Две группы маршрутов API с разными правами

**Статус:** принято; расширено [ADR-0005](0005-multi-user-model.md) — с многопользовательской
моделью две группы становятся тремя, по одной на роль доступа (оператор, пользователь,
приложение)

## Контекст

У HTTP API два вида потребителей: внешние приложения, которые ходят за данными по своему
ключу и должны получать новые платёжные адреса, и оператор шлюза (через фронтенд), который
настраивает шлюз и выполняет команды. Приложения не должны иметь возможности настраивать шлюз
и выполнять команды.

## Решение

Один HTTP-сервер, одно ядро (оркестратор), две группы маршрутов с разными правами:

- **API приложений** — доступ по ключу приложения (API-key): чтение данных (балансы,
  поступления, статусы) и выдача нового платёжного адреса. Маршрутов настройки и команд в
  этой группе не существует — они отсутствуют как маршруты, а не «запрещены проверкой прав».
- **Админское API** — полноценная аутентификация оператора: настройка и команды. Может быть
  привязано к отдельному порту или только к локальному интерфейсу — тогда снаружи оно не
  видно.

## Рассмотренные альтернативы

- **Одна группа маршрутов с проверкой ролей:** отклонено — пропущенная проверка на любом
  маршруте превращается в повышение привилегий; физически раздельные группы делают границу
  структурной.
- **Два отдельных API-сервиса:** для старта отклонено как эксплуатационно более тяжёлое;
  разделение на группы уже даёт нужную границу внутри одного сервера.

## Последствия

- Граница для приложений структурная: нечего неправильно настроить на отдельном маршруте.
- Админскую поверхность можно полностью скрыть из сети.
- Фронтенд пользуется админским API (плюс чтением данных при необходимости); приложения —
  только API приложений.
