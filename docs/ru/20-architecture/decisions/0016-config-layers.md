# ADR-0016: Уровни конфигурации

**Статус:** принято

## Контекст

У шлюза конфигурация двух разных природ: то, что нужно процессу до открытия какой-либо
базы, и то, чем оператор управляет во время работы (включая API-ключи провайдеров данных).
Одно хранилище на обе роли не годится: параметры подключения не могут жить внутри базы,
которую они открывают, а управляемые оператором значения не должны требовать доступа к
консоли сервера и перезапусков.

## Решение

- **Переменные окружения — только развёрточный уровень (bootstrap)**: путь к каталогу
  данных шлюза, адрес/порт API, а при переходе на PostgreSQL — строка подключения к
  реестровой базе. Их изменение — действие развёртывания; перезапуск ожидаем.
- **Таблица `settings` реестра — всё, чем оператор управляет на ходу** (дополняет
  [ADR-0008](0008-shared-registry-db.md)): API-ключи провайдеров данных (TronGrid и
  будущие), темп запросов и суточный бюджет по провайдерам, пороги подтверждений по
  сетям, интервалы watcher, включённые сети. Управляется через панель оператора: внести,
  заменить или отозвать ключ провайдера — без консоли сервера и без перезапуска.
- Секреты не появляются в коде, журналах и репозитории — ни на одном уровне.

## Рассмотренные альтернативы

- **Всё в переменных окружения:** отклонено — управляемые оператором значения (прежде
  всего ключи провайдеров) требовали бы доступа к консоли сервера и перезапуска для
  замены и ротации.
- **Всё в базе данных:** отклонено — параметры подключения не могут жить внутри
  открываемой ими базы; развёрточные значения — не епархия оператора во время работы.

## Последствия

- Резервная копия реестра содержит ключи провайдеров — ещё один довод обращаться с
  копиями реестра как с чувствительными (там и так хеши паролей); ключ провайдера
  отзывается в одну кнопку в его консоли.
- Будущее API оператора получает операции настроек; конфигурационный модуль бэкенда
  читает уровень окружения один раз на старте.
