# ADR-0025: Экземпляры приложения — пространство имён пользователей приложения

**Статус:** принято; уточняет [ADR-0009](0009-address-bindings-primary-mode.md) (идентичность
пользователя приложения) и [ADR-0011](0011-application-api-principles.md) (состав операций
API приложений)

## Контекст

Одно приложение может быть развёрнуто несколькими независимыми установками: движок магазина,
переданный нескольким владельцам, или боевая и тестовая среды одной интеграции. Такие
установки настраиваются одинаково и приходят к шлюзу с одним общим ключом API.

Идентификатор пользователя приложения уникален в рамках приложения
([ADR-0009](0009-address-bindings-primary-mode.md)), поэтому «пользователь 42» одной
установки и «пользователь 42» другой оказываются одним и тем же пользователем приложения.
Шлюз выдаёт им один платёжный адрес; средства двух разных плательщиков попадают на один адрес
и в один баланс, и различить их больше нечем. Для платёжного шлюза это худший класс ошибки.

Несколько копий **одного** развёртывания за балансировщиком — другая ситуация, и в ней делать
нечего: база у копий общая, один и тот же идентификатор означает одного и того же человека, а
идемпотентная выдача и без того возвращает каждой копии один адрес.

## Решение

- Идентичность пользователя приложения становится тройкой **приложение + экземпляр +
  внешний идентификатор**. Экземпляр — произвольная строка, которую выбирает вызывающая
  сторона; шлюз её не интерпретирует, ровно как и сам внешний идентификатор.
- **Измерение живёт у пользователя приложения, а не у привязки.** Привязки ссылаются на
  строку пользователя приложения по внутреннему номеру, поэтому уникальность привязки,
  уникальность адреса и переиспользование индекса деривации между сетями разделяют установки
  сами, без единой собственной правки.
- **Экземпляр по умолчанию — пустая строка, а не литерал вроде `main`.** Это идиома, уже
  принятая в схеме для `bindings.memo` и `assets.contract_address`: пустая строка вместо
  NULL, потому что NULL в SQL не равен NULL и уникальность с ним не работает. Приложение с
  единственной установкой **и есть** пустой экземпляр — не особый случай в коде, а
  существующие строки остаются верны после миграции без переноса данных и без перевыпуска
  адресов.
- **Значение едет параметром запроса `instance`.** В API приложений он объявлен один раз в
  зависимости, разбирающей вызывающего, поэтому попадает сразу во всю группу маршрутов и не
  может быть забыт при добавлении нового: маршрута этой группы без такой зависимости не
  существует. Маршруты кабинета принимают тот же параметр под тем же именем и с тем же
  значением по умолчанию. Отсутствует или пуст — экземпляр по умолчанию.
- **API приложений всегда ограничено экземпляром вызывающего**, включая список
  пользователей: пользователи чужой установки для него не существуют, а не «запрещены».
  Кабинет показывает владельцу все экземпляры сразу, называя экземпляр явно.
- **Общий ключ означает общее доверие.** Экземпляр разделяет учёт, а не безопасность:
  установки, делящие ключ, могут назвать экземпляр друг друга. Там, где нужна настоящая
  граница, дорога — свой ключ на установку (см. альтернативы).

## Рассмотренные альтернативы

- **Отдельное приложение на установку:** работает уже сегодня без единой правки, но дублирует
  соответствие «сеть → кошелёк» в каждом приложении и забивает кабинет почти одинаковыми
  записями. Отклонено как основной путь; остаётся верным ответом, когда установки принадлежат
  разным владельцам и не должны видеть друг друга.
- **Экземпляр у привязки:** отклонено — коллизия живёт в пространстве имён идентификаторов, а
  оно принадлежит пользователю приложения. У привязки экземпляр пришлось бы вносить в три
  ограничения уникальности, держать в согласии со строкой пользователя приложения — и всё
  равно два разных плательщика делили бы одну строку пользователя и одну строку в кабинете.
- **Литерал `main` как значение по умолчанию:** отклонено — `main` остаётся значением, которое
  приложение может прислать явно, поэтому пустая строка и `main` были бы двумя одинаково
  выглядящими пространствами имён. Чтобы этого избежать, слово пришлось бы зарезервировать и
  нормализовать ввод — машинерия, купленная ради названия.
- **Экземпляр в заголовке запроса:** отклонено — заголовки шлюза несут аутентификацию
  (`X-API-Key`) и защиту от подделки межсайтовых запросов, и деловое измерение среди них
  ломает это простое правило. Параметр запроса виден в порождаемой спецификации OpenAPI,
  проходит обычную проверку ввода и сохраняет симметрию кабинета и API приложений. Гарантию
  «нельзя забыть» даёт общая зависимость, а не транспорт.
- **Экземпляр в пути** (`/v1/app/instances/{экземпляр}/users/{ид}/…`): выражает идентичность
  полнее всего, но пустой сегмент пути не адресуется, поэтому экземпляру по умолчанию
  понадобилась бы заглушка или вторая форма маршрута — и адреса всех существующих интеграций
  изменились бы.
- **Свой ключ на экземпляр внутри одного приложения:** сильнейший вариант по безопасности —
  экземпляр приезжает из ключа, подделать его нельзя, доступ отзывается поштучно, а
  соответствие сетей остаётся общим. Отложено, не отклонено: требует вынести ключ приложения
  из строки приложения в отдельную таблицу. Модель данных выше при этом не меняется, поэтому
  переход обойдётся без переноса данных и без перевыпуска адресов.

## Последствия

- Существующие интеграции не затронуты: они и есть экземпляр по умолчанию, их адреса не
  меняются.
- Каждый новый экземпляр расходует новые индексы деривации того же кошелька, поэтому счётчик
  адресов кошелька растёт быстрее. Это верно: разным плательщикам нужны разные адреса.
- Имя экземпляра едет в адресе запроса и потому попадает в журналы обратного прокси. Называйте
  экземпляры нейтрально (`shop-2`), а не именем клиента.
- Страница приложения в кабинете перечисляет пользователей всех экземпляров и называет
  экземпляр отдельной колонкой; счётчик пользователей приложения остаётся общим по приложению.
- Обратный шаг миграции возможен, только пока экземпляр один: восстановление прежнего
  ограничения упадёт, если две установки успели завести одинаковый идентификатор, — и это
  правильный исход, потому что иначе пришлось бы молча выбросить чьи-то привязки.
