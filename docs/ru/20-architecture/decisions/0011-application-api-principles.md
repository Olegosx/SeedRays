# ADR-0011: Принципы API приложений

**Статус:** принято

## Контекст

API приложений обслуживает основной режим
([ADR-0009](0009-address-bindings-primary-mode.md)): приложения запрашивают адреса для своих
пользователей и читают, что пришло. Приложения не должны узнавать о внутренних сущностях
владельца, а подметание средств с адресов — техническая процедура владельца, которая
приложений не касается.

## Решение

Операции (семантический уровень; точные форматы запросов и ответов — отдельный шаг):

1. **Создание адреса** для пользователя приложения — в одной сети, нескольких или во всех
   доступных приложению. Идемпотентно: существующая привязка возвращается как есть. Первый
   запрос для неизвестного пользователя приложения создаёт его запись неявно — отдельной
   операции «зарегистрировать пользователя» нет.
2. **Получение адреса (адресов)** пользователя приложения — только чтение; ничего не
   создаёт.
3. **Получение балансов** пользователя приложения — строки «сеть + актив», фильтры по сети
   и активу. В каждой строке: всего поступлений (по подтверждённым) и «ожидается».
   Текущий остаток адреса приложениям не отдаётся.
4. **Получение истории входящих транзакций** — те же фильтры плюс фильтр статуса
   (по умолчанию — подтверждённые; неподтверждённые и неуспешные — по явному запросу);
   с пагинацией.
5. **Список пользователей приложения** — с пагинацией.

Принципы:

- **Приложения оперируют только сетями.** Владелец настраивает приложению соответствие
  «сеть → кошелёк» в кабинете; «все сети» — все сети, настроенные таким образом. Кошельков
  приложения не видят.
- **Пагинация**: параметр количества строк, по умолчанию 10, 0 — все.
- **Соглашения**: версия API в пути (`/v1/…`); везде JSON; суммы — строками, никогда не
  числами с плавающей точкой; API-ключ — в заголовке запроса, никогда не в URL; единый
  формат ошибок (машинный код + человекочитаемое сообщение).
- **Уведомления webhook — запланированное расширение** (шлюз обращается по URL,
  зарегистрированному приложением, при новых поступлениях — вместо постоянного опроса).
  Не в первой версии; дизайн API не должен этого исключать.

## Рассмотренные альтернативы

- **Указание кошелька в запросе приложения:** отклонено — вытаскивает внутренние сущности
  владельца наружу и усложняет ключи.
- **Отдача приложениям текущего остатка адреса:** отклонено — подметание — процедура
  владельца; приложению нужно знать, что пришло (подтверждённое и ожидаемое), а не что
  сейчас лежит на адресе.
- **Отдельная операция «зарегистрировать пользователя»:** отклонено — неявное создание при
  первом запросе адреса означает меньше состояний и меньше ошибок.

## Последствия

- API пользователя (кабинет) должно включать управление соответствием «сеть → кошелёк» по
  каждому приложению.
- Модель данных получает это соответствие как часть сущности «приложение».
- Webhook входит в план как точка расширения.
