# ADR-0023: Журнал событий безопасности — точность внутри, нейтральность наружу

**Статус:** принято

## Контекст

Маршруты аутентификации сознательно отвечают нейтрально: «нет такого пользователя» и
«не тот пароль» — один и тот же `invalid_credentials`, запрос сброса пароля не
раскрывает существование адреса. Для атакующей стороны это правильно — но оператор,
разбирающий инцидент, остаётся с той же размытой картиной. Шлюзу нужен журнал,
фиксирующий, что произошло на самом деле. Таблица в базе рассмотрена и отклонена: при
переборе каждый отбитый запрос вставлял бы строку (~2,5 ГБ/сутки уже при скромных
100 запросах/с), и каждая вставка конкурировала бы за блокировку записи SQLite с
финансовыми записями watcher.

## Решение

- **Точность внутри, нейтральность наружу**: записи журнала несут настоящую причину —
  `wrong_password`, `unknown_identifier`, `user_blocked`, `unknown_email`,
  `unconfirmed_email`, … — а ответы API остаются ровно теми же. Причины фиксируются
  там, где они ещё известны: внутри операций входа и сброса, до нейтрализации;
  остальное — на уровне маршрутов.
- **Файл с ротацией, а не база**: JSON Lines в `logs/security.log` в каталоге данных
  шлюза. Одно событие — один JSON-объект: время, роль (пользователь/оператор), тип
  события, исход, идентификатор как введён, найденный id пользователя/оператора, адрес
  клиента, детали события. Ротация по размеру со сжатием архивов gzip (штатные
  средства библиотеки `logging`, новых зависимостей нет).
- **Ротация настраивается оператором**: ключи реестра `seclog.rotate_mb` (размер файла
  до ротации, по умолчанию 100 МБ) и `seclog.backups` (сколько сжатых архивов хранить,
  по умолчанию 10) на странице настроек панели; применяются при перезапуске шлюза.
  Худший потолок диска — `rotate_mb × (backups + 1)`; gzip обычно ужимает архивы на
  порядок ниже него.
- **Чего в журнале не бывает никогда**: паролей, токенов сессий и сброса, решений
  капчи, значений настроек (при изменении настроек записываются только **ключи**).
  Сбой журнала не валит саму операцию — доступность аутентификации первична; поломка
  отмечается один раз в обычном логе процесса.
- **Покрытие**: вход пользователя, регистрация, сброс пароля (запрос и подтверждение),
  смена пароля, отказы капчи и лимитов; вход и смена пароля оператора;
  административные действия оператора — блокировка/разблокировка пользователя, сброс
  пароля пользователя, изменение настроек.

## Рассмотренные альтернативы

- **Таблица в реестре**: удобные выборки и будущий экран панели, но неограниченный
  рост под атакой и конкуренция за блокировку записи на горячем пути входа; отклонена.
- **Обычный лог процесса**: смешивает события безопасности с эксплуатационным шумом и
  не имеет по-событийной структуры; отклонён как основное хранилище (эксплуатационные
  строки остаются).

## Последствия

- Журнал содержит чувствительные метаданные (кто, когда и откуда входил). Принятая
  цена точности: идентификатор, ошибочно введённый в поле логина — включая пароль,
  вписанный туда по ошибке, — попадает в журнал как есть. Файл живёт только в каталоге
  данных шлюза и доступен тому, кто управляет сервером.
- За обратным прокси в колонке адреса пока значится адрес прокси — известное
  ограничение, общее с тормозом перебора; чинится вместе с поддержкой реального IP до
  развёртывания.
- Сжатие при ротации синхронное: единственный процесс замирает на секунду-другую,
  когда полный файл уходит в архив, — под атакой примерно раз в час, вне её — редко.
- Экран чтения журнала в панели сознательно отложен: оператор самоустанавливаемого
  шлюза читает файл напрямую (`tail`, `jq`).
