# Обзор архитектуры

Общая структура системы: бэкенд + фронтенд.

## Подход к проектированию

Бэкенд построен по принципу «library-first» (сначала библиотека): вся бизнес-логика живёт в
импортируемых модулях с чистыми интерфейсами, а каждая точка входа — консольные команды,
HTTP API — лишь тонкая обёртка над этими модулями. Один код обслуживает автономные команды,
оркестратор и тесты без дублирования. См. [ADR-0001](decisions/0001-library-first-core.md).

Шлюз многопользовательский с первого дня: каждая операция оркестратора и каждый вызов
хранилища несут контекст пользователя. Пользователь владеет одним или несколькими кошельками;
доступ разделён на три роли — оператор шлюза (суперадмин), пользователь (владелец кошельков)
и приложения пользователя. См. [ADR-0005](decisions/0005-multi-user-model.md).

## Бэкенд

Основа бэкенда — [оркестратор](components/orchestrator.md): сервисный слой, в котором живёт
бизнес-логика шлюза и который вызывает три функциональных компонента как обычные
Python-модули:

- [Генератор ключа](components/key-generator.md) — порождает сид и ключи кошелька.
- [Модуль деривации](components/derivation.md) — выводит платёжные адреса из расширенного
  публичного ключа (xpub).
- [Watcher](components/watcher.md) — наблюдает за балансами и поступлениями по кошелькам
  всех пользователей.

Онлайн-часть шлюза — наблюдающая (watch-only): она хранит только xpub, умеет выводить адреса,
но не может ничего подписывать. См. [ADR-0002](decisions/0002-watch-only-online-part.md).

Весь доступ к блокчейну идёт через слой [абстракции блокчейна](components/chain-abstraction.md).
Внешний интерфейс — [HTTP API](components/http-api.md).

Стек бэкенда — Python 3.14, FastAPI + uvicorn, SQLAlchemy Core + Alembic, httpx, bip-utils,
argon2-cffi — зафиксирован в [ADR-0013](decisions/0013-backend-stack.md).

### Модель процессов

Бэкенд работает одним процессом. При старте оркестратор запускает HTTP API-сервер и watcher
параллельно (потоками или асинхронными задачами) и присматривает за обоими: сбой одного
записывается в журнал, компонент перезапускается, второй продолжает работать. Полная
независимость на уровне процессов — заготовленный путь эволюции: модульная структура делает
будущее разделение дешёвым. См. [ADR-0003](decisions/0003-single-process-supervised.md).

### Хранение данных

У каждого пользователя — своя база данных и рабочая директория
(см. [ADR-0005](decisions/0005-multi-user-model.md)). Помимо них шлюз ведёт небольшую общую
реестровую базу — реестр пользователей, индекс API-ключей, учётные записи операторов и общие
настройки, без финансовых данных
(см. [ADR-0008](decisions/0008-shared-registry-db.md)). Весь доступ к данным идёт через
[слой хранения](components/storage.md) — интерфейс уровня операций предметной области,
скрывающий конкретную базу: первая реализация — SQLite, далее PostgreSQL и MySQL.
См. [ADR-0006](decisions/0006-storage-abstraction.md). Структура хранимых данных описана в
документе [Модель данных](data-model.md).

### Структура пакета

```
backend/
  seedrays/              — Python-пакет (ядро)
    keygen/              — генерация ключа
    derivation/          — деривация адресов из xpub
    watcher/             — «один проход» + постоянный цикл
    chains/              — абстракция «источник данных цепочки»; реализации: tron/, …
    storage/             — интерфейс хранения уровня предметной области; реализации: sqlite/, …
    orchestrator/        — сервисный слой, бизнес-логика
    api/                 — тонкий HTTP-слой поверх оркестратора
    cli.py               — консольные команды (keygen, derive, watch, …)
  tests/
frontend/                — статика без сборки (многостраничный HTML + ES-модули, vendor/)
```

## Фронтенд

Фронтенд даёт кабинет пользователя и интерфейс оператора. С бэкендом он общается только через
[HTTP API](components/http-api.md) и никогда не обращается к внутренностям бэкенда напрямую.

Реализован как статика без сборки: многостраничный HTML с ES-модулями, комплект Tabler и
Alpine.js завендорены в репозиторий, Node.js отсутствует — осознанное решение по цепочке
поставки для софта финансового сектора. См. [ADR-0012](decisions/0012-frontend-stack.md).
