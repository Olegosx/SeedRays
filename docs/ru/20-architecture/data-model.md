# Модель данных

Концептуальная структура данных шлюза: сущности, их поля и связывающие их правила. Точные
определения таблиц (типы, индексы) закрепляются на этапе реализации. Где какие данные живут —
задано [ADR-0005](decisions/0005-multi-user-model.md) и
[ADR-0008](decisions/0008-shared-registry-db.md); сети, активы и финансовые структуры —
[ADR-0010](decisions/0010-networks-assets-financial-data.md).

## Пользовательская база

### Привязки

Основная таблица соответствия (см.
[ADR-0009](decisions/0009-address-bindings-primary-mode.md)): кошелёк, сеть, адрес, мемо,
приложение, пользователь приложения.

- Одна привязка на «кошелёк + сеть + приложение + пользователь приложения». Кошелёк несёт
  семейство (TRON, EVM, …); привязка называет конкретную сеть.
- В сетях с мемо привязку идентифицирует пара «адрес + мемо»; много привязок могут разделять
  один адрес.
- Ссылка на приложение хранится рядом со ссылкой на пользователя приложения намеренно
  (дешёвая фильтрация по приложению); согласованность двух ссылок обеспечивается на уровне
  схемы.
- Индекс деривации переиспользуется между сетями для одной пары «кошелёк + пользователь
  приложения» — EVM-кошелёк тогда даёт плательщику одинаковый адрес во всех сетях
  семейства; иначе выделяется следующий свободный индекс кошелька. Внутри одной сети
  индекс уникален для кошелька (на уровне схемы), а выделение сериализовано по
  пользователю — два плательщика никогда не получат один адрес.
- Финансовых данных нет.

### Приложения

Единица подключения к шлюзу (см.
[ADR-0009](decisions/0009-address-bindings-primary-mode.md)): принадлежит пользователю
шлюза, идентифицируется своим API-ключом (индекс «хеш ключа → пользователь» живёт в общем
реестре). Несёт соответствие «сеть → кошелёк», настраиваемое владельцем в кабинете, — сами
приложения кошельков не видят (см.
[ADR-0011](decisions/0011-application-api-principles.md)).

### Пользователи приложений

Внутренний id, приложение, экземпляр, внешний идентификатор — произвольная строка, которую
присылает приложение; шлюз её не интерпретирует.

- **Экземпляр** — пространство имён внешних идентификаторов
  (см. [ADR-0025](decisions/0025-application-instances.md)): независимые установки одного
  приложения ходят общим ключом API, и их собственная нумерация пользователей
  сталкивается. Поэтому идентичность — тройка «приложение + экземпляр + внешний
  идентификатор», уникальная на уровне схемы.
- Экземпляр — произвольная строка, которую шлюз не интерпретирует, ровно как и внешний
  идентификатор. Приложение с единственной установкой пользуется **пустым** экземпляром —
  пустая строка, а не NULL, по той же причине, что и мемо у привязки: NULL в SQL не равен
  NULL, и уникальность с ним не работает.
- Привязки ссылаются на внутренний id этой строки, поэтому экземпляр разделяет
  плательщиков, вообще не появляясь в таблице привязок.

### Балансы

Одна строка на «адрес + актив»: текущий баланс, всего поступлений, дата/время последнего
поступления.

- Производные данные: обновляются в той же транзакции БД, что и простановка отметки
  «учтена в балансе», и в любой момент пересчитываемы из таблицы транзакций.
- Учитываются только финализированные успешные транзакции; ожидающее финальности —
  вычисление по таблице транзакций, платежи в очереди видны в таблице мемпула.

### Транзакции (в блокчейне)

Одна таблица для транзакций, попавших в цепочку
(см. [ADR-0017](decisions/0017-universal-tx-model.md),
[ADR-0021](decisions/0021-two-phase-scanning.md)): адрес, идентификатор транзакции,
актив, направление, номер события, сумма, **номер блока (обязателен — «в блокчейне»
значит в блоке)**, время, **статус исполнения (успех / провал)**, время первой встречи,
**отметка финализации** (ставится, когда авторитетное сканирование финализированной зоны
подтверждает строку) и служебная отметка **«учтена в балансе»** — ставится ровно один
раз, в той же транзакции БД, что и обновление баланса.

- Строка без отметки финализации — **предварительная**: увидена выше границы
  финальности; показывается как ожидающая, балансов не касается и удаляется, если
  финализированная цепь её не подтвердит (реорганизация). Финализированные строки
  только добавляются.
- Провальные строки (в блоке, но исполнение провалилось — например, REVERT / нехватка
  энергии) на балансы не влияют никогда; хранятся для разбора споров.
- Идемпотентность: повторное сканирование тех же диапазонов не должно создавать дублей —
  уникальный ключ «идентификатор транзакции + адрес + актив + направление + номер
  события» (направление закрывает перевод самому себе; номер события — несколько
  переводов одного актива внутри одной транзакции, например батч-выплаты).

### Очередь (мемпул)

Наблюдения транзакций в очереди — разосланных, но не попавших ни в один блок
(см. [ADR-0017](decisions/0017-universal-tx-model.md)): номера блока нет; строки могут
висеть (низкокомиссионные транзакции EVM) или исчезать. Универсальная сущность модели:
наполняется только там, где источник данных сети видит очередь (проиндексированные
провайдеры TRON — нет; источники EVM и свои ноды — да).

## Общая реестровая база

Помимо реестра пользователей, индекса API-ключей, учёток операторов и настроек
(см. [ADR-0008](decisions/0008-shared-registry-db.md)):

### Почты пользователя

Адреса, привязанные к учётной записи (основная + добавленные): адрес (уникален по всему
шлюзу, в нижнем регистре), признак «основная», время подтверждения. Подтверждение — по
одноразовому токену из письма ([ADR-0020](decisions/0020-mail-provider.md)): в базе —
только отпечаток SHA-256 токена и срок его действия.

### Сессии кабинета

Кука браузера несёт случайный токен; в базе — его отпечаток SHA-256, пользователь, срок
действия (7 дней, с «запомнить меня» — 30) и CSRF-токен, который сверяется с заголовком
`X-CSRF-Token` каждого изменяющего запроса. Просроченные строки чистятся при входе.

Сессии панели оператора — отдельная таблица того же устройства (срок — 1 день):
куки и группы маршрутов операторов и пользователей не пересекаются. Токены сброса
пароля — отпечаток одноразового токена из письма со сроком действия; у пользователя
не больше одного действующего токена.

### Справочник активов

Сетеспецифичные справочные данные: сеть, нативная монета или контракт токена, символ,
десятичность. USDT в TRON и USDT в Ethereum — два разных актива; семейство (например, EVM)
здесь не встречается — только конкретные сети. Справочник пополняется автоматически, когда
watcher впервые видит новый актив: шлюз не ограничивает список принимаемых активов — честно
записывает всё, что пришло; фильтрация — дело потребителя.

### Индекс xpub кошельков

Уникальность подключённых xpub по всему шлюзу (один xpub — один кошелёк), по аналогии с
индексом ключей API: отпечаток SHA-256 xpub и пользователь-владелец. Сам xpub живёт
только в базе владельца; повторное подключение отклоняется той же нейтральной ошибкой,
что и битый ключ, — ответ не раскрывает, что xpub уже где-то подключён.

### Служебное состояние watcher

По каждой сети: курсоры авторитетного финализированного сканирования
(см. [ADR-0018](decisions/0018-range-scanning.md),
[ADR-0021](decisions/0021-two-phase-scanning.md)) — последний обработанный
финализированный блок и временной курсор скана токенов; сканирование возобновляется от
них с перекрытием, а дубли гасятся уникальным ключом таблицы транзакций. Не финансовые
данные.

## База биллинга

Расчётные данные владельца шлюза — вознаграждение, которое он берёт с пользователей
(см. [ADR-0027](decisions/0027-gateway-fee-billing.md)). Отдельная база, потому что в реестре
финансовым данным не место, а база пользователя переезжает, восстанавливается из копии и
уходит в архив вместе с ним.

> Запланировано ADR-0027; в коде пока нет.

### Мастер-кошельки владельца

По одному на сеть оплаты: сеть, xpub уровня аккаунта, время внесения. Ключ наблюдающий,
как и у пользователей; уникальность xpub по всему шлюзу распространяется и на него —
совпадение дало бы один адрес двум владельцам сразу, и watcher не знал бы, чьё это
поступление.

### Адреса счетов

Постоянное соответствие «пользователь + сеть оплаты → адрес + индекс деривации». Адрес
выдаётся один раз и служит всем последующим счетам пользователя: платёж опознаётся
адресом получателя, а число адресов остаётся равным числу платящих пользователей, а не
числу выставленных счетов.

### Счета

Одна строка на «пользователь + период», уникальность на уровне схемы: границы периода,
оборот периода в USDT, применённые ставка и порог, сумма к оплате, срок оплаты, сеть и
адрес оплаты, состояние (выставлен / оплачен / просрочен), зачтённая сумма, время
выставления и время оплаты.

- Ставка, порог и срок — снимок настроек на момент выставления: позднейшее изменение
  настроек не переписывает уже выставленные счета.
- Оборот хранится итогом: это результат расчёта по транзакциям пользователя, а не ссылка
  на них.

### Платежи по счетам

Поступления, наблюдаемые на адресах счетов: адрес, идентификатор транзакции, актив,
сумма, время, отметка финализации — и зачёт: к какому счёту отнесено и сколько зачтено.
Ручное подтверждение оператором — строка того же вида с пометкой «подтверждено вручную»,
оператором и причиной.

- Переплата остаётся незачтённым остатком и зачитывается в следующий счёт; отдельной
  сущности «аванс» нет — это состояние выводится из платежей.
- Поступление чужого актива на адрес счёта записывается, но ни к какому счёту не
  относится.

### Состояние биллинга пользователя

Сеть оплаты (по умолчанию TRON) и состояние доступа: в порядке или приостановлен за
неуплату, с временем приостановки. Состояние независимо от статуса учётной записи в
реестре — административная блокировка и приостановка за неуплату снимаются каждая своим
действием.

### Что считается оборотом

Успешные финализированные входящие операции пользователя по активам из списка оператора
(адреса контрактов, не символы). Перекладывание средств между собственными адресами
доходом не считается: у такой операции в той же транзакции есть исходящая нога того же
пользователя на ту же сумму того же актива — этого достаточно, чтобы её распознать, и
хранить контрагента в транзакции для этого не нужно.
