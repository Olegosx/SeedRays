# HTTP API

Тонкая обёртка над [оркестратором](orchestrator.md): маршруты, проверка входных данных, коды
ответов. Собственной бизнес-логики не содержит.

## Группы маршрутов

Три группы над одним ядром — по одной на роль доступа
(см. [ADR-0004](../decisions/0004-two-api-groups.md) и
[ADR-0005](../decisions/0005-multi-user-model.md)):

- **API приложений** — для внешних приложений пользователя, доступ по ключу приложения
  (API-key). Даёт чтение данных и запрос постоянных привязок адресов для пользователей
  приложения (см. ниже) — в рамках кошельков пользователя, которому принадлежит ключ.
  Маршрутов настройки и команд в этой группе не существует.
- **API пользователя (кабинет)** — для владельца кошельков, с аутентификацией пользователя.
  Даёт управление своими кошельками (передача xpub или генерация ключа в шлюзе), своими
  приложениями и их ключами, соответствием «сеть → кошелёк» по каждому приложению, а также
  просмотр своих данных.
- **API оператора** — для оператора шлюза (суперадмина), с полноценной аутентификацией
  оператора. Даёт управление пользователями и общими настройками шлюза, включая управление
  watcher. Может быть привязано к отдельному порту или только к локальному интерфейсу —
  тогда снаружи оно не видно.

В каждой группе граница структурная: маршрутов операций чужой роли в группе не существует —
они отсутствуют как маршруты, а не «запрещены проверкой прав».

## Операции API приложений

Семантический состав (см. [ADR-0011](../decisions/0011-application-api-principles.md)):

- **Создание адреса** для пользователя приложения — в одной сети, нескольких или во всех
  доступных приложению. Идемпотентно: существующая привязка возвращается как есть. Первый
  запрос для неизвестного пользователя приложения создаёт его запись неявно.
- **Получение адреса (адресов)** пользователя приложения — только чтение; ничего не создаёт.
- **Получение балансов** пользователя приложения — строки «сеть + актив», фильтры по сети и
  активу; в каждой строке: всего поступлений (по подтверждённым) и «ожидается». Текущий
  остаток адреса не отдаётся: подметание средств — техническая процедура владельца,
  приложения она не касается.
- **Получение истории входящих транзакций** — те же фильтры плюс фильтр статуса
  (по умолчанию — подтверждённые; неподтверждённые и неуспешные — по явному запросу);
  с пагинацией.
- **Список пользователей приложения** — с пагинацией.

Каждая операция ограничена **экземпляром приложения**, от имени которого пришёл вызов
(см. [ADR-0025](../decisions/0025-application-instances.md)): независимые установки одного
приложения ходят общим ключом API, и экземпляр разделяет идентификаторы их пользователей.
Список пользователей приложения ограничен так же — пользователи чужой установки для
вызывающего не существуют. Приложение с единственной установкой экземпляр не называет и
работает ровно как прежде.

Приложения оперируют только сетями: владелец настраивает приложению соответствие
«сеть → кошелёк» в кабинете; «все сети» — все сети, настроенные таким образом.

Пагинация: параметр количества строк, по умолчанию 10, 0 — все.

## Соглашения

- Версия API в пути (`/v1/…`).
- Везде JSON; суммы — строками, никогда не числами с плавающей точкой.
- API-ключ — в заголовке запроса, никогда не в URL.
- Единый формат ошибок: машинный код + человекочитаемое сообщение.

## Запланированные расширения

- **Уведомления webhook**: приложение регистрирует URL, шлюз обращается по нему при новых
  поступлениях — вместо постоянного опроса. Не в первой версии; дизайн API не должен этого
  исключать.

## API приложений: реализованные маршруты

```
POST /v1/app/users/{ид}/addresses   [?instance=]  тело: {"networks": ["tron"] | "all"}
GET  /v1/app/users/{ид}/addresses   [?instance=&network=]
GET  /v1/app/users/{ид}/balances    [?instance=&network=&asset=]
GET  /v1/app/users/{ид}/history     [?instance=&network=&asset=&status=&limit=]
GET  /v1/app/users                  [?instance=&limit=]
```

- **Аутентификация**: ключ приложения — в заголовке `X-API-Key`. Ключи — случайные токены
  высокой энтропии, хранятся хешами SHA-256: медленное хеширование (Argon2) — для
  человеческих паролей, где оно защищает от перебора; случайный 256-битный токен перебором
  не берётся, а медленный хеш лишь тормозил бы каждый запрос.
- **Статусы** отображаются на модель транзакций ADR-0017: `confirmed` — учтена в балансе;
  `pending` — записана, ещё не учтена; `failed` — провал исполнения.
- Параметр `instance` называет экземпляр приложения
  ([ADR-0025](../decisions/0025-application-instances.md)); отсутствует или пуст —
  экземпляр по умолчанию, которым и пользуется приложение с единственной установкой.
  Объявлен один раз в зависимости группы, разбирающей вызывающего, поэтому действует на
  всех маршрутах сразу и не может быть забыт при добавлении нового. Общий ключ означает
  общее доверие: экземпляр разделяет учёт, а не безопасность.
- Фильтр `asset` принимает адрес контракта токена или литерал `native`.
- Ошибки: `{"error": {"code", "message"}}`; ошибки валидации — в том же формате.
- Интерактивная OpenAPI-спецификация генерируется фреймворком на `/docs`.

## API пользователя: реализованные маршруты

```
GET    /v1/user/captcha           (подписанная proof-of-work задача, ADR-0022)
POST   /v1/user/register          тело: {"username", "email", "password", "captcha"}
GET    /v1/user/confirm-email     ?token=…   (ссылка из письма; переадресует на вход)
POST   /v1/user/login             тело: {"identifier", "password", "remember", "captcha"}
POST   /v1/user/logout
GET    /v1/user/me
GET    /v1/user/networks          (сети, семейства и шаблоны ссылок на обозреватель блоков)
GET    /v1/user/wallets
POST   /v1/user/wallets           тело: {"family", "xpub", "label"}
POST   /v1/user/wallets/generate  тело: {"words", "families", "passphrase"}
GET    /v1/user/applications
POST   /v1/user/applications      тело: {"name"} → ключ (показывается один раз)
GET    /v1/user/applications/{id}
GET    /v1/user/applications/{id}/users/{ид}/addresses  [?instance=]
POST   /v1/user/applications/{id}/users/{ид}/addresses  [?instance=]  тело: {"networks": ["tron"] | "all"}
POST   /v1/user/applications/{id}/key        (перевыпуск — новый ключ один раз)
DELETE /v1/user/applications/{id}/key        (отзыв)
PUT    /v1/user/applications/{id}/networks   тело: {"network", "wallet_id"}
DELETE /v1/user/applications/{id}/networks/{network}
GET    /v1/user/history      [?wallet_id=&network=&asset=&status=&limit=&cursor=]
GET    /v1/user/overview     (счётчики, поступления по активам, последние операции)
POST   /v1/user/emails       тело: {"address"}   (вторая почта, подтверждение письмом)
DELETE /v1/user/emails/{id}                      (основную удалить нельзя)
POST   /v1/user/password     тело: {"current_password", "new_password"}
POST   /v1/user/password-reset          тело: {"email", "captcha"}
POST   /v1/user/password-reset/confirm  тело: {"token", "new_password"}
```

Смена пароля гасит все остальные сессии пользователя (текущая остаётся).

Выпуск адресов из кабинета (`POST …/users/{ид}/addresses`) — тот же самый вызов ядра,
что и одноимённый маршрут [API приложений](#api-приложений-реализованные-маршруты):
владелец шлюза может выдать адрес руками,
не поднимая интеграцию. Свойства наследуются целиком — идемпотентность (повтор возвращает
уже выданное), неявная регистрация ранее не встречавшегося пользователя приложения,
ошибка `network_not_configured` для сети вне карты приложения. Параметр `instance` — тот
же, что и у API приложений, под тем же именем и с тем же значением по умолчанию
([ADR-0025](../decisions/0025-application-instances.md)): владелец выпускает адрес в
названную установку, пустое значение означает экземпляр по умолчанию. Чтение приложения
(`GET /v1/user/applications/{id}`) перечисляет пользователей **всех** экземпляров и
называет экземпляр каждого — владельцу нужна полная картина, в отличие от приложения.

История кабинета листается «показать ещё» (решение владельца): ответ несёт
`next_cursor` — непрозрачную позицию последней выданной строки; передача его в `cursor`
продолжает список строго за ней, поэтому появление новых операций сверху не сдвигает и
не дублирует уже показанное. Отсутствие `next_cursor` — конец списка.

Сброс пароля: ответ запроса всегда одинаковый — существование адреса не раскрывается;
письмо уходит только на подтверждённую почту. Токен из письма одноразовый (в базе — его
отпечаток, срок — 1 час, новый запрос вытесняет прежний), ссылка ведёт на страницу
нового пароля; успешный сброс гасит все сессии пользователя. Без настроенной почты —
`mail_not_configured` даже в режиме разработки: сброс без письма не существует. Запросы
ограничены тем же тормозом перебора.

- **Сессия** — кука HttpOnly, Secure (SameSite=Lax); в базе хранится отпечаток токена.
  Изменяющие запросы обязаны нести заголовок `X-CSRF-Token`, выданный при входе и в
  `/me`; проверка — единая структурная зависимость каждого изменяющего маршрута
  (сравнение за постоянное время), забыть её при добавлении маршрута невозможно.
- Регистрация: имя пользователя 3–64 знака без пробелов и `@`; пароль от 8 знаков; почта
  приводится к нижнему регистру. Письмо подтверждения — через отправителя почты
  ([ADR-0020](../decisions/0020-mail-provider.md)); ссылка подтверждения строится только
  из настройки `gateway.base_url` (заголовку Host доверия нет), настроенный отправитель
  без этой настройки не используется. Без настроенной почты исход явный: регистрация
  отвечает `mail_not_configured`, пока оператор не включил режим разработки с
  авто-подтверждением (`mail.dev_autoconfirm`).
- Тормоз перебора: вход и регистрация ограничены скользящими окнами в памяти процесса
  (для входа — по клиенту и идентификатору, для регистрации — по клиенту); сверх лимита
  ответ 429 `rate_limited`. Адрес клиента за доверенным обратным прокси определяется из
  `X-Forwarded-For` (настройка `gateway.trusted_proxies`; у соединений с
  неперечисленных адресов остаётся адрес соединения — подделать заголовок снаружи
  нельзя).
- Proof-of-work капча ([ADR-0022](../decisions/0022-pow-captcha.md)): вход, регистрация
  и запрос сброса несут поле `captcha` — решение задачи из `GET /v1/user/captcha`,
  которое браузер вычисляет незаметно. Задачи подписаны HMAC, живут 10 минут и
  принимаются ровно один раз; проверка идёт после тормоза перебора, отказ отвечает
  400 `captcha_failed`.
- Вход: одно поле идентификатора (имя или почта); до подтверждения основной почты вход
  закрыт (`email_not_confirmed`); «нет такого пользователя» и «не тот пароль» дают
  одинаковый ответ `invalid_credentials`. Точная причина уходит в журнал безопасности
  ([ADR-0023](../decisions/0023-security-journal.md)) — нейтральны ответы, но не журнал.
- Приложения: сам ключ не хранится — в базе пользователя его отпечаток и открытые первые
  символы для опознания, в реестре — индекс «отпечаток → владелец»; сырой ключ
  возвращается ровно один раз при создании и перевыпуске; отзыв обнуляет отпечаток и
  удаляет строку индекса — доступ приложения закрывается немедленно.
- Кошельки: прикрепление проверяет xpub выводом нулевого адреса. Расширенный ПРИВАТНЫЙ
  ключ отклоняется отдельным кодом `private_key_rejected` — пользователя предупреждают,
  что такой ключ надо считать скомпрометированным. Xpub, уже подключённый где-либо на
  шлюзе, отклоняется тем же нейтральным ответом `invalid_xpub`, что и битый ключ (ответ
  не должен раскрывать, что ключ используется). Генерация в шлюзе (ADR-0002)
  **без состояния** — фраза создаётся в памяти запроса и возвращается ровно один раз
  вместе с xpub каждого семейства, ничего не записывается; после проверки записи фразы
  браузер прикрепляет кошельки обычным путём «семейство + xpub», так что сид не
  передаётся по сети повторно.
- Статику фронтенда может раздавать сам процесс шлюза (ADR-0012): `/` переадресует на
  страницу входа, файлы — из каталога `frontend/` (переопределяется настройкой
  `frontend_dir` конфигурационного файла, развёрточный уровень ADR-0016 и
  [ADR-0026](../decisions/0026-configuration-file.md)).

## API оператора: реализованные маршруты

```
GET  /v1/operator/captcha    (подписанная proof-of-work задача, ADR-0022)
POST /v1/operator/login      тело: {"login", "password", "captcha"}
POST /v1/operator/logout
GET  /v1/operator/me
POST /v1/operator/password   тело: {"current_password", "new_password"}
GET  /v1/operator/users
POST /v1/operator/users/{id}/status          тело: {"status": "active"|"blocked"}
POST /v1/operator/users/{id}/password-reset  → временный пароль (один раз)
POST /v1/operator/users/{id}/delete          тело: {"username"} (логин, набранный оператором)
GET  /v1/operator/settings
PUT  /v1/operator/settings   тело: {"values": {ключ: значение}}
GET  /v1/operator/watcher    (курсоры watcher по сетям, только чтение)
```

- Сессия панели — собственная кука HttpOnly/Secure, отдельная от кабинета; CSRF,
  тормоз перебора и proof-of-work капча — те же механизмы, что в группе пользователя
  (у панели свой выпуск задач — граница групп остаётся структурной). Учётные записи
  операторов создаются только консольной командой `seedrays operator-create`.
- Секретные настройки в ответах не появляются — только признак «задано»; пустой секрет
  при сохранении означает «не менять». Блокировка пользователя завершает его сессии,
  и его приложения теряют доступ к API приложений немедленно.
- Удаление пользователя ([ADR-0024](../decisions/0024-user-deletion-archive.md)) —
  только заблокированного (`user_not_blocked` иначе); присланный `username` сверяется
  с логином удаляемого (`username_mismatch` при расхождении). Данные переезжают в
  серверный архив; восстановление — консольной командой `seedrays user-restore`.
