# Слой хранения

Интерфейс между логикой шлюза и базой данных. Компоненты выше него SQL не видят вообще.

## Уровень интерфейса

Абстракция проведена на уровне операций предметной области — «сохрани поступление», «дай
адреса кошелька», «отметь адрес занятым» — а не на уровне «универсального SQL». Конкретная
реализация выполняет эти операции своим диалектом.
См. [ADR-0006](../decisions/0006-storage-abstraction.md). Это тот же принцип, что у
[абстракции блокчейна](chain-abstraction.md): компоненты выше интерфейса не знают, что под
ним.

## Хранение по пользователям

У каждого пользователя — своя база данных и рабочая директория
(см. [ADR-0005](../decisions/0005-multi-user-model.md)):

- Изоляция структурная: запрос физически не может дотянуться до данных другого пользователя.
- Жизненный цикл пользователя (резервная копия, перенос, удаление) — операция над одним
  каталогом.
- Конкуренция записи в SQLite размазана по файлам пользователей; используется режим журнала
  WAL, чтобы читатели не блокировались писателем.

## Общая реестровая база

Помимо пользовательских баз шлюз ведёт одну небольшую общую базу с реестровой ролью
(см. [ADR-0008](../decisions/0008-shared-registry-db.md)): реестр пользователей с учётными
данными для входа, индекс API-ключей, учётные записи операторов, общие настройки шлюза,
справочник активов и служебное состояние watcher по сетям
(см. [ADR-0010](../decisions/0010-networks-assets-financial-data.md)). Финансовых данных в
ней нет — кошельки, адреса, привязки и операции живут только в пользовательских базах.

## Реализации

- **SQLite** — первая реализация: база пользователя — файл в его директории.
- **PostgreSQL, MySQL** — следующие по плану. Как изоляция «по пользователю» ляжет на
  серверную СУБД (база на пользователя или схема на пользователя) — открытый вопрос,
  который будет решён отдельным ADR при подключении PostgreSQL.

## Миграции

Миграции схемы прогоняются циклом по всем пользовательским базам; инструмент миграций должен
уметь это с самого начала. Выбор реализации (SQLAlchemy Core + Alembic или свой тонкий слой
над стандартными драйверами) — открытый вопрос, который будет решён отдельным ADR на этапе
реализации (новые зависимости — по согласованию).
