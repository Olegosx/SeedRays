# Сценарии кабинета пользователя

Сценарии работы пользователя (владельца кошельков) в личном кабинете: что человек
делает и зачем. Документ пишется до реализации и служит основой для проектирования
API пользователя и страниц фронтенда.

> Документ в работе: сценарии добавляются по мере согласования.

## Учётная запись и способы входа

Учётная запись и способ входа — разные понятия. Учётная запись одна: имя пользователя,
почта, статус; это владелец кошельков, весь остальной шлюз знает только её идентификатор.
Способов входа у учётной записи может быть несколько, и все они — разные пути прийти к
одной и той же учётной записи:

- **пароль** — базовый способ первого этапа (хранится хешем Argon2 при учётной записи);
- **внешние сервисы авторизации (OAuth)** — подключаются на следующих этапах без переделки
  базы и архитектуры: отдельная сущность «внешняя личность» — пара «провайдер +
  идентификатор пользователя у провайдера», уникальная и указывающая на учётную запись.
  Новый провайдер — это новые строки этой сущности и реквизиты в настройках, а не изменение
  существующих таблиц.

Любой способ входа завершается одинаково: установлена личность → найдена учётная запись →
выдана сессия. Кабинет и права не зависят от того, каким способом вошёл пользователь.

Привязка внешнего сервиса выполняется из кабинета уже вошедшим пользователем; отвязка —
там же, с ограничением: нельзя удалить последний способ входа. Политика автоматической
привязки при первом входе через провайдера (по совпадению подтверждённой почты) — открытый
вопрос, решается при проработке сценария внешнего входа.

## Регистрация

- Регистрация самостоятельная: почта + имя пользователя + пароль.
- Почта и имя пользователя уникальны в рамках шлюза. В имени пользователя запрещён символ
  `@` — иначе имя могло бы совпасть с чужой почтой в общем поле входа.
- Почта подтверждается письмом. Реквизиты отправки почты (SMTP) — настройка оператора в
  реестре (уровень настроек [ADR-0016](../20-architecture/decisions/0016-config-layers.md)).

## Вход

- Одно поле идентификатора + пароль; в поле идентификатора равнозначно принимаются имя
  пользователя и почта (поиск сначала по имени, затем по почте — оба уникальны,
  неоднозначность исключена).

## Восстановление пароля

- Основной путь: ссылка для сброса на подтверждённую почту.
- Запасной путь: сброс пароля оператором из его панели (пользователь потерял доступ к
  почте).

## Язык интерфейса

Интерфейс двуязычный с самого начала: русский и английский. Язык определяется как
«сохранённый выбор → язык браузера → английский»; переключатель — на странице входа и в
настройках профиля. Техническое устройство —
[ADR-0019](../20-architecture/decisions/0019-frontend-localization.md) (клиентские
словари, одна вёрстка на все языки).

## Структура кабинета

Боковое меню из пяти разделов плюс выход:

- **Дашборд** — сводка по кабинету (наполнение будет определено отдельно).
- **Кошельки** — список кошельков, добавление кошелька двумя путями
  ([ADR-0002](../20-architecture/decisions/0002-watch-only-online-part.md): передать xpub
  или сгенерировать ключ в шлюзе), адреса кошелька.
- **Приложения (API)** — управление приложениями: создание приложения, выпуск и отзыв его
  API-ключа, настройка соответствия «сеть → кошелёк», просмотр пользователей приложения и
  их адресов. API-ключ принадлежит приложению, поэтому раздел устроен по приложениям.
- **История операций** — входящие операции по всем кошелькам с фильтрами (кошелёк, сеть,
  актив, статус).
- **Настройки** — личные настройки владельца кабинета: профиль (почта, имя), язык
  интерфейса и безопасность — смена пароля, способы входа (привязка и отвязка внешних
  сервисов).
  Общешлюзовых настроек в кабинете нет — они только в панели оператора.
- **Выход** — элемент меню, не раздел.

Адреса и привязки отдельного раздела не имеют: адреса пользователей приложения
просматриваются внутри приложения, адреса кошелька — внутри кошелька.

## Кошельки

### Список кошельков

Список кошельков пользователя. Состав строки списка — уточняется.

### Прикрепление кошелька (рекомендуемый путь)

Путь «внешняя генерация» из
[ADR-0002](../20-architecture/decisions/0002-watch-only-online-part.md): ключи созданы вне
шлюза, передаётся только публичная информация.

- Форма: семейство (TRON, EVM, …), xpub уровня аккаунта, метка.
- Шлюз проверяет xpub: корректность формата и выводимость адресов.
- Секреты в этом пути не участвуют; в интерфейсе он подаётся как рекомендуемый.

### Создание кошелька в шлюзе (на свой страх и риск)

Путь «генерация в шлюзе» из ADR-0002; требования к обращению с секретом зафиксированы в
[генераторе ключа](../20-architecture/components/key-generator.md) и
[модели угроз](../30-security/threat-model.md): только HTTPS, секрет не пишется в журналы,
базу и сохраняемые ответы, память очищается после показа.

Сценарий:

1. Пользователь явно выбирает длину сид-фразы: 12 или 24 слова.
2. Семейства выбираются галочками; с одной фразы создаётся по кошельку на каждое
   отмеченное семейство (одна фраза даёт xpub каждого семейства).
3. Кодовая фраза (passphrase) — по желанию, галочкой, открывающей поле ввода; рядом —
   предупреждение: забытая кодовая фраза — навсегда потерянные средства.
4. Сид-фраза показывается ровно один раз под запись.
5. Подтверждение записи: пользователь вводит три произвольно запрошенных слова фразы
   (например, 3-е, 7-е и 11-е). Кошельки создаются только после успешного подтверждения;
   шлюз сохраняет только xpub — по одному на отмеченное семейство.
